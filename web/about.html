Raytracer / Realtime Engine

A from-scratch C++17 renderer and game engine — running here live in your browser via WebGPU and WebAssembly.

100% AI-written

Every line of this engine was written by AI. I haven't written a single line of code myself. It is prompted from start to finish using Anthropic's Claude models (Opus and Fable) — the architecture, the three render backends, the physics and procedural-generation systems, the shaders, and this page.

It's a personal experiment: how far can you get building a modern rendering and game engine purely by prompting an AI — and then use that engine as a personal toolchain to explore procedural generation and simulation? This site is the running result.

What you're looking at

Everything in the gallery is a procedurally generated scene rendered in real time by a custom engine written from scratch in C++ (standard library only, no game-engine framework). The same engine also runs natively on desktop and as an offline path tracer — the thumbnails on the gallery were path-traced by that offline renderer. In the browser it's compiled to WebAssembly and draws through WebGPU, the modern low-level GPU API.

How it's organized

The engine talks to one abstract renderer interface; each platform plugs in behind it.

The key idea: engine code never names a graphics API. It calls one Renderer interface, and each platform supplies one implementation, chosen when the program is built. Adding a platform means writing a new implementation — not editing the engine. That's why the exact same ECS, physics, procedural generation, and gameplay run unchanged whether the pixels come from Metal, Vulkan, or WebGPU.

The three renderers

Metal

The macOS/iOS backend and the feature reference the others are matched against.

Vulkan

The Linux/Windows backend. Shaders are GLSL compiled to SPIR-V bytecode.

WebGPU

The browser backend running this page — compiled to WebAssembly, shaders written in WGSL.

Each GPU API speaks a different shading language, so the shaders are three hand-written trees kept behaviorally identical. Every frame runs the same pipeline: shadow maps → lit scene into a high-dynamic-range buffer → screen-space ambient occlusion, reflections, and bloom → a final tone-mapping pass to the screen.

Running in the browser

The C++ is compiled to WebAssembly with Emscripten; WebGPU (navigator.gpu) is the GPU API. A single-threaded design keeps it simple — no special server headers needed. The whole thing is a static site: no backend, no accounts, nothing stored. Use the Quality preset in the viewer's panel (⚙) to trade fidelity for frame rate — it auto-picks a lighter tier on phones.
