Buildings: the shape grammar and the architectural toolkit

Every building in a city is grown from three things: its lot's polygon, a few hundred bytes of parameters, and the height of the ground. A lot becomes a rectangle on a site plan, a recipe fills in the parameters, a mass gives an outline at every storey, a facade grammar splits each wall into bays and openings, and the same storey outlines feed the interior, the colliders and a reachability gate. This page follows one lot through all of it.

The problem

A city has thousands of buildings, and none of them is modelled by hand. Each one has to look like a believable building from across the river and from the pavement, stand on its lot without crossing a road, have a front door on the street, and, since enterable buildings landed (ADR-0080), be a real place inside: a lobby, stairs and lifts to every floor, rooms with furniture, a way onto the roof. The outside and the inside must agree to the centimetre, or the player walks through a window or into a wall.

Three ideas carry the whole system:

Grow, don't store

A building is a pure function of (plan, params, baseY). The city stores the inputs (the regen key) and regrows the meshes whenever it needs them: the interior when the player walks up to a door, a wall again when its neighbour turns out to be shorter.

One answer, many readers

Where a door is, where a window is, what each storey's outline is: each is decided once (storeyPlans, facadeLayout, the core) and read by the facade, its far tier, the inner walls, the furniture, the collider and the graph.

Words, not one-offs

A new shape is a new word in the grammar (a transform on a stack, a cell in a complex), never a private grower. Glenn, 2026-10-15: "it needs to be done using the building shape grammar and not a one off function or chunk of code".

The older buildings page describes the grammar as it stood before the site plans and the toolkit (recipes, tripartite composition, the facade grammar, roofs, the style book). It is still a good picture of the facade vocabulary; this page is the current pipeline.

Lots and the site plan

A block is a face of the road graph (see roads). The parceller walks the block's edges and lays lots along each street (by default frontWidth 16 m wide and lotDepth 28 m deep), mitred at the corners, with the leftover middle as one court; only a block the walk cannot fill falls back to recursive bisection of its oriented bounding box (parcel.h). Every lot keeps a frontage vector pointing at its street, which is how a building knows where its front door goes.

Lots beside a non-square corner come out as trapezoids, because the walk clips each strip by the corner's bisector. Until September the grammar extruded that trapezoid verbatim, so every building filled its lot and many had a slanted wall. ADR-0086 put a blueprint layer in between, on the rule buildings are rectilinear; lots are not; the difference is paving, planting, a plaza or a yard:

Left: a 34 m lot whose side lines lean in, with residential yards (front 3 m, side 1.5 m, rear 5 m). SiteFrame sits on the frontage edge: u along the street, v inward. Right: the same lot rastered on the frame (drawn at 1 m; the code uses 0.5 m); a cell is kept when its centre is in the lot and at least its edge's yard from every edge. The blue block is the largest rectangle of kept cells, here 23 × 12 m. The ground left over is cut by the rectangle's lines into a forecourt, side yards and a rear yard (openSpacePieces). largestAlignedRect: the classic largest-rectangle-in-a-histogram scan over the kept cells src/engine/procgen/city/site_plan.cpp
    // Largest rectangle of 1s: per row, a histogram of consecutive usable
    // cells above, and the classic stack scan for the widest bar span.
    std::vector<int> height(nx, 0), stack;
    int bestArea = 0, bi0 = 0, bi1 = -1, bj0 = 0, bj1 = -1;
    const int minCells = std::max(1, static_cast<int>(std::ceil(minSide / cell)));
    for (int j = 0; j < ny; ++j) {
        for (int i = 0; i < nx; ++i)
            height[i] = mask[static_cast<std::size_t>(j) * nx + i] ? height[i] + 1 : 0;
        stack.clear();
        for (int i = 0; i <= nx; ++i) {
            const int h = i < nx ? height[i] : 0;
            while (!stack.empty() && height[stack.back()] >= h) {
                const int top = stack.back();
                stack.pop_back();
                const int hh = height[top];
                const int left = stack.empty() ? 0 : stack.back() + 1;
                const int width = i - left;
                if (hh >= minCells && width >= minCells && hh * width > bestArea) {
                    bestArea = hh * width;
                    bi0 = left; bi1 = i - 1;
                    bj0 = j - hh + 1; bj1 = j;
                }
            }
            stack.push_back(i);
        }
    }

The raster never asks about roads (that check walks every road edge and is far too slow per cell). Instead the lot pass searches the lot, then the lot inset by 0.8, 1.6, 2.6 and 3.6 m, until the rectangle's corners and edge midpoints clear the road corridors (city_lots.cpp, the SITE PLAN block in PASS C). Yards come per district from BlockInfo::yards: financial and commercial 0 / 0.3 / 3 m, old town 0 / 0.3 / 2, industrial 2 / 2 / 2, residential 3 / 1.5 / 5 (ADR-0086). Downtown, the leftover ground is not grass: an urban lot is paved to its lot line at the pavement's height, and the building's base is that paving, so a downtown door is flush with the street.

How it got here. The first thing ADR-0086 built was a census, which put numbers on the complaint: on piedmont_mini only 26.4 % of buildings had no oblique corner. After the site plan: 92.1 % (lanelab metro 59.5 → 81.5 %, lattice metro 54.9 → 86.9 %). Coverage fell by about a quarter, and the lattice metro's tallest tower lost ten floors (50 → 40), because the slenderness cap reads the plate's short side and the honest rectangle is smaller than the trapezoid's bounding box had flattered it. Rejected: snapping the polygon's corners inside the grammar (the grammar must stay pure in its inputs), and making the parceller emit rectangles ("the lots are trapezoids in a real city; it is the building that is not"). Gate: grown_buildings_stand_on_rectilinear_footprints holds nine in ten buildings rectilinear. Glenn later asked to keep the occasional trapezoid: a lot no rectangle fits keeps its shape rather than going green.

Open lots. A lot that does not build still gets a use (ADR-0144): before it falls back to grass, emitGreen offers it a car park, a playground, a community garden or a pocket park, in an order set by district, with about 15 % left vacant on purpose. On island_8_nature 2,223 of 13,156 lots had been bare grass; afterwards there were 17 car parks, 180 playgrounds, 293 gardens and 1,356 pocket parks. Each sculptor works on the largest rectangle square to the lot's street edge (largestFrameRect), in the same SiteFrame (since ADR-0173 the one plan frame every lot sculptor uses).

The architect: recipes, districts and height

The architect (architect.h) decides what stands on a lot. The city is zoned into five DistrictTags (Financial, Commercial, Residential, OldTown, Industrial); each district has a weighted table of named recipes, and every lot asks architectPick(tag, shortSide, area, seed, coreness). Coreness is how deep downtown the lot sits (1 at the centre, 0 at the rim), and it is what peaks the skyline. Landmarks (capitol, courthouse, hospital, a school per quarter) are not rolled per lot but placed on the best-scoring lots by quota (planLandmarks), and a whole block the parceller could not fill becomes one landmark site (architectBlockLandmark). The registry holds 79 named recipes, from cottage and rowhouses to bundled_tubes and mall_complex.

recipeGlassTower: a recipe is a function that fills BuildingParams from its own dice src/engine/procgen/city/architect.cpp
void recipeGlassTower(BuildingRecipe& out, Hash& rng, RecipeCtx& cx) {
    BuildingParams& p = out.params;
    // Density round ("taller than 40 stories"): dead-centre coreness lifts
    // the glass cluster to 55-62 floors; the rim keeps its 10-16.
    const int lift = static_cast<int>(cx.coreness * 46);
    p.floors = rng.irange(cx.roomy ? 10 : 6, cx.roomy ? 16 : 9) + lift;
    p.groundRetail = true;
    dress(p, FacadeStyle::GlassCurtain, rng);
    if (p.floors > 8) { p.setbackFloors = rng.irange(4, 6);
                        p.setbackEvery = rng.range(1.2, 1.8); }
    if (p.floors > 16) p.setbackFloors = rng.irange(5, 7);
    cx.slender = 3.0 + cx.coreness * 4.5;
    // ...
    if (cx.roomy && rng.unit() < 0.35)
        out.massing = BuildingRecipe::Massing::Circle;
    else if (cx.roomy && cx.coreness > 0.4 && rng.unit() < 0.5)
        out.massing = BuildingRecipe::Massing::TowerInPlaza;
    out.placeType = "office";
    if (p.curtainWall) glassStyle(p, rng, true);   // every glass tower its own glass (NYC variety M2)
    towerTop(p, {{2, 30}, {4, 12}, {3, 10}, {5, 10}, {6, 10}, {8, 6}, {7, 4}, {1, 18}});   // buildings M2
    out.name = "glass_tower";
}

Two rules keep recipes honest. The slenderness cap: after the recipe, capFloors limits the floors so the building is no taller than its plate's short side times slender (1.8 for most recipes; the tower recipes ask for more, rising with coreness). Height drives structure and cladding (ADR-0040): load-bearing masonry does not scale (the Monadnock Building's six-foot brick base is the classic example), so from about 12 storeys a real wall becomes a curtain wall hung off a frame. In the code this is a property of the recipe tables rather than one function: tall recipes dress GlassCurtain, the masonry recipes roll short floor counts, and the architect's tests hold the tables coherent (architect_tables_are_coherent: the rim keeps to 16 floors). Storey heights follow use too: an office floor is 3.9–4.1 m floor to floor, a tower lobby 6–8 m, a flat 3.2 m (storeyHeightsByUse).

The regen key and the records

Everything the recipe decided lands in one plain struct, BuildingParams (shape_grammar.h): floors and storey heights, bay width, cladding part and colours, window style, roof, the massing envelope and its numbers, the curtain-wall style, the core switch, party walls, links to neighbouring cells, the shop mix. It is deliberately a POD of numbers, not polygons, so it serialises byte for byte into the lot cache (kBuildingParamsSize = 824 in lot_cache.cpp, version 23) and so the exterior and the interior derive the same tiers from it. A grown building's runtime identity is a record:

BuildingRecord: what the runtime keeps of a building src/engine/procgen/city/building_records.h
struct BuildingRecord {
    Poly2 plan;
    Real baseY = 0;    // wall base (pad + plinth)
    Real groundY = 0;  // graded pad plane
    Real height = 0;   // massing height above baseY
    BuildingParams params;
    std::vector<DoorSpec> doors;
    bool enterable = false;
    std::string recipe, type, district;
    std::vector<Vec3> beacons;   // aviation lamp centres (BeaconLightSystem's sprites and lights)
    std::vector<RoofItem> roof;  // what stands on the roof: the collider's walls, the roof cell's holes
};

The records sit in a 24 m spatial hash (CityBuildings) so the interior system can ask "which building contains this point" cheaply. Interiors are grown at run time from the record, so an interior change needs no re-bake. Exteriors are baked into the lots bundle, so a change to the exterior grammar or the lot pass bumps kLotsBuildTag (lots_producer.cpp) and every lots bundle rebuilds (see bakes).

How the main types relate. StoreyPlan[] is the hub: the facade, the core, the rooms and the graph all read the same outlines, which is why the inside and the outside agree.

The mass and the stack: a form becomes storeys

Before the toolkit, a building was one straight-edged polygon in one frame, copied storey by storey in nested tiers (the setbacks and envelopes of ADR-0086). The architectural toolkit (ADR-0174, issue #105) replaced that model with two foundations. Foundation B, the exterior model, starts from the mass: anything that can give its outline at a height (a slice) and its skin as a mesh.

Mass: the one interface every form sits behind src/engine/procgen/city/mass.h

struct Mass {
    virtual ~Mass() = default;

    virtual Real height() const = 0;               // to the top of the last storey
    virtual MassBounds bounds() const = 0;

    // form where the source has one (a sweep's or an SDF's polygonised skin); a stack's is the loft either way.
    virtual RenderMesh shell(int lod, const Vec3& colour) const = 0;
};

// THE BRIDGE into the storey view: storey 0 the ground (the base slice, `groundHeight` tall), then `floors`

std::vector<StoreyPlan> sliceStoreys(const Mass& mass, const BuildingParams& params);

sliceStoreys is the slice bridge: it asks the mass for its outline at the ground and then at each floor height, and hands out StoreyPlans. Everything downstream (the facade, the room planners, the collider, the census) reads storey plans and does not care which kind of mass made them. The mass sources are:

The stack is the workhorse. Every older massing (the uniform setbacks, the 1916 street wall and its steps, the sky exposure plane, the taper, the slab, the feathered pencil tower) is now a preset: a stack with identity transforms, built by stackOf. It was proven byte-identical before anything new was added (the_stack_preset_slices_to_todays_storeys_bit_for_bit). A new form is a transform on an entry, never new tier code.

sliceStoreys: the slice bridge from any mass to the storey view src/engine/procgen/city/mass.cpp
std::vector<StoreyPlan> sliceStoreys(const Mass& mass, const BuildingParams& params) {
    std::vector<StoreyPlan> out;
    const Slice base = mass.slice(-1.0);
    if (base.empty()) return out;
    out.push_back({base.outline().tessellate(), 0, params.groundHeight, 0});
    Real y = params.groundHeight;
    for (int i = 0; i < params.floors; ++i) {
        const Slice s = mass.slice(y);
        if (s.empty()) break;
        out.push_back({s.outline().tessellate(), y, params.floorHeight, s.tier});
        y += params.floorHeight;
    }
    return out;
}

The Section under each entry (section.h) is an outline made of edges (line, arc, spline-owed) with holes, rather than a bare polygon. It knows its arcs, so a rounded corner's chords are each one even facade bay (tessellateForBays), and it has exact rectilinear surgery (chamfer, notch) and Clipper2 booleans (unite, subtract, intersect) that re-tag chord runs as arcs afterwards. Ruled glass. When a storey is turned or scaled against the one above and both outlines have the same corners, each edge's curtain wall is a ruled face: its bottom edge on this storey's floor outline, its top on the ceiling's, so a twist reads as one continuous surface (FaceRect::ruled, planEdgeRuled). Where corners do not correspond (a field's contours), each storey is a flat facet and a slab band, the union of the two outlines, closes the seam. Glenn, walking the first twisted tower: "they look like layered cakes"; the ruled faces landed the same evening (ADR-0175).

Implicit masses and envelopes

Some forms are not any transform of one outline. The implicit mass (ADR-0177) is the engine's SDF kit with building words on top: sdfPlan (2D distance to a polygon), sdfExtrude, and sdfWave, a warp of the space the field is read in. A storey is the field's zero contour at the storey's mid height: sliceSdf samples a half-metre grid offset off the field's own lines, traces it by marching squares, keeps the largest loop and simplifies it by Douglas–Peucker within 0.3 m.

The first implicit form taught a design rule. Glenn, on the wavy tower's first cut: "the interior of those offices should just be a straight edge versus the exterior which can be wavy". So the envelope (ADR-0178) lets any form be either the floors or a skin round straight floors, by BuildingParams::skin: 0 the form is the floors; 1 a double skin (straight floors a gap inside, the form a glass veil ruled storey to storey); 2 plates (each floor plate runs out to the form's contour, Aqua Tower's waving balconies, with railings on the edges past the glass); 3 both. The straight floors are the plan scaled about its centre until they fit inside the form at every storey; if they would be narrower than the core needs, the form is the floors after all. The same ADR added the glass caps: dome, spire, vault, aperture and flared, one lofted emitter with a profile per kind.

Two rules from Glenn govern every non-prismatic form (ADR-0174): it is always glass (brick and stone stay on straight walls), and a style ships only as "a real building, fully accessible, inside and out, base to roof".

The facade grammar, step by step

The split grammar of ADR-0038 is CityEngine's CGA idea: take a scope (an oriented box) and rewrite it by splitting, repeating and insetting until each piece is a wall panel, a window or a door. In this engine the rule that does that for every building is facadeLayout. It takes one FaceRect (one plan edge of one storey: a bottom-left corner, a horizontal and vertical axis, a normal, a width and a height) and a mode (Entrance, Retail, Residential, Solid, Rear, PartyDoor, StairDoor), and returns the bays and every opening's span, sill and head. Here it is applied to one wall: the 17.5 m street edge of a three-floor walk-up with no shops (groundRetail = false, bayWidth 3.5 m, ground storey 4.5 m, floors 3.2 m).

One rule, applied to one wall. (1) The plan edge, extruded from the ground to the roof, is the face; the parapet sits above it. (2) The storey stack splits it vertically: storey 0 at 4.5 m, three storeys of 3.2 m, 14.1 m to the roof (these come from sliceStoreys, not from the facade). (3) Each storey's face is repeated across into lround(17.5 / 3.5) = 5 bays of 3.5 m: the bay count is rounded, so the bay stretches a little to fill the wall exactly. (4) Each bay splits into pier, opening, pier: a window module of 1.25 m (the bay minus 0.8 m, capped portrait), the piers absorbing the rest (1.125 m each), the sill at 0.9 m and the head at 2.4 m above the storey floor. On storey 0 the face is in Entrance mode, so the centre bay (bays / 2 = bay 2) is the door instead: 2.0 m wide, 2.7 m high. Numbers computed from the code below.

Why it is shaped this way:

  • The layout is decided once. facadeLayout returns data (FacadeLayout: bays, bay width, a BayOpening per bay), not geometry. The full-detail facade, the flat far tier, the inner wall of the streamed interior, the fire escape, the shop rooms and the furniture's list of windows (storeyOpenings) all read it, so a window cannot be in two places. The arch's rise moved into it for the same reason: an arched window used to be square from inside and from across the street (Glenn, 2026-09-15).
  • Constant window module. The window stays 1.25 m on a wide face and a narrow one; the piers absorb the slack (ADR-0040). A bay too narrow for 0.55 m of glass becomes a blank bay, encoded as a zero-height opening so every reader fills it with wall.
  • Human scale is pinned. The sill, head, door and parapet are named constants in namespace human (shape_grammar.h), so a door the grammar cuts is one the player's capsule fits through. ADR-0038 planned about 2.1 m; on 4.5 m lobby storeys that read as "front doors are very short", so it is 2.7 m.
  • Modes come from the plan. groundModeFor picks each ground edge's mode: Entrance on the edge facing the street, Retail on the others when the building has shops, Solid on a vehicle-bay front or a party wall, Rear for the back door. Above the ground every storey is Residential (or Solid), and the curtain wall has its own emitter on the same face.

Where the CGA vocabulary went. ADR-0038 describes an interpreter that rewrites scopes by ops (split, repeat, comp, inset ...). Those ops exist (splitScope, repeatScope, insetScope in shape_grammar.h, bound to Lua as Scope:split / :divide / :inset), but at this commit no building calls them; the only C++ caller is the car interior (car_interior.cpp). Buildings are grown by growPlanBuilding walking the storey plans and calling facadeLayout per edge: the same split/repeat logic, written as one function per rule rather than as a rule interpreter.

The complex: buildings made of cells

A Sears Tower, a perimeter block round a courtyard, twin towers with a sky bridge, a mall with anchor stores: these are several masses standing against each other. The complex (ADR-0176, cells.h) does them without a mesh boolean: each cell is a mass in its own frame with its own params, grown as the ordinary plan building it is, and where two cells touch the shared faces become party walls. Complex::resolve finds them: two edges on one line, facing each other, overlapping by at least 2 m.

A party wall is stored on the params as a world line (outward normal partyN, offset partyAt), with partyTop, the last storey it is blank on (0 = to the roof). The taller cell keeps its windows above the lower one's roof. Every reader that knows its storey asks partyEdge(plan, params, edge, storey):

bool partyEdge(const Poly2& plan, const BuildingParams& params, std::size_t e, int storey) {
    const int k = partyWallOf(plan, params, e);
    if (k < 0) return false;
    if (storey >= 0 && params.partyTop[k] > 0 && storey > params.partyTop[k]) return false;   // above the neighbour's roof
    return true;
}

The presets so far: bundledTubes (the Sears pattern), courtyardWings (eight cells: four wings and four corners, because a party wall is a whole edge and four wings cannot share half an edge), ringCells (one trapezoid cell per edge of a convex outline, round a court), twinTowers and mallCells. connectLobbies gives every cell a way in, and opens a doorway both ways through every whole shared wall on the ground, so a bundle's ground floors are one lobby (ADR-0179). openWall removes a shared wall along a run, floor to ceiling, on chosen storeys: an anchor store open onto a mall concourse (ADR-0180). The facade draws the wall in two pieces either side, the collider leaves it out (wallCuts is the one list of cuts both read), the furniture keeps it clear, and the space graph gets a link cell through it.

The sky bridge was drawn, cut and counted by its tests, and still could not be crossed: on 2026-10-21 Glenn, at the top of a twin tower: "I'm standing in front of a skybridge and I can't cross it!" The streamed interior's own inner-wall collider (a plane 0.55 m inside every facade) sealed the door, and the far tower was never grown because the interior system only grew buildings near a street door (ADR-0222). Both were fixed and the test now walks a capsule across: a_walker_crosses_the_sky_bridge_between_twin_towers (stopped 0.87 m short before, 16.2 m across after).

Party walls between ordinary buildings

The same party-wall fields serve attached buildings on a dense street: the lot pass marks a lot's shared side lines, pushes the rectangle out to them, and blanks the wall. But PASS C grows one lot at a time, so a building does not know its neighbour's height when it grows, and every party wall went up blank to the roof: a glass tower beside a walk-up showed a whole grey side. ADR-0227 added a pass after PASS C that sets each wall's partyTop from what actually stands against it (the neighbour's highest storey still on the line, or any building within 6 m) plus a 1 m sill, and regrows each changed building, cutting its first growth out of the merged part meshes. On island_8_nature 1,005 of 3,446 attached buildings took windows above a lower neighbour; the lots stage went from 145 to 160 s.

Inside: the space graph

Foundation A of the toolkit is the interior model. A building is a set of cells, the volumes a person can be in (a room, a storey's hall, a stair shaft, a hoistway, the roof deck, a helipad, a bridge), joined by portals, the openings a person passes through. A cell is three-dimensional: a stair shaft is one cell that spans every storey it serves. A storey plan is a view of the graph, not the model.

Migration, not replacement. The graph is not yet what the interior is grown from. On its first day it found three real faults: apartment end units that were a dead end past the bath, coreless setback towers whose straight stair ended at the first shrunken tier (every storey above had no way up), and a ring office on an L's narrow arm whose door opened onto the outside wall. A physics test backs each kind of portal, because a graph edge only says a walker should get through: a door walk, the stairwell, the cab ride, the bridge, the straight stair through a setback (character_climbs_the_straight_stair_through_a_setback), and the acceptance ride character_rides_the_cab_to_the_twentieth_floor_and_takes_the_stairs, which walks a Jolt capsule in from the street, round the lobby desk, up 20 floors standing on the moving cab and up a flight of stairs.

Inside: cores and streamed interiors

Interiors are not baked. ADR-0080 made doorways real holes and put the enter/exit logic in a system: BuildingInteriorSystem grows a building's interior with growInterior when the player comes within 6 m in front of a door, and frees it past 40 m. The interior is pure in the record's regen key, so it is the same every time. Measured on a condo: grow 0.25 ms plus 0.51 ms of Jolt body creation, synchronous on purpose.

A building of four floors and up gets a core when one fits (ADR-0086 point 11): two enclosed dog-leg stairwells (two 1.2 m flights either side of a 0.2 m spine) at the ends of a bank of 2.4 × 2.6 m hoistways (one up to eight floors, two to twenty, three to forty, four beyond), a closed service block behind, seated in the centre of the top tier so every tier below contains it, with a 2.2 m corridor ring kept inside every tier. Since the toolkit, the core is the first preset of a CirculationPlan of shafts, banks and zones (circulation.h), and the shafts become stair and lift cells in the graph. Inside: floor plans and furniture

A storey's rooms come from roomPlan / storeyRooms (room_plan.h), which picks a topology by the plate: a ring of rooms along the outside walls round an open middle (offices behind a curtain wall, flats behind masonry), a whole floor that is one dwelling (a masonry plate under 13 m on its short side, no core: a house), or apartments off a corridor round the core. Room partitions land on the facade's bay lines, so a wall meets a pier or a mullion, never a pane. Before a house floor ships, floorIsWalkable floods a 0.15 m grid from the front door with the walls inflated by the capsule's radius; a floor that fails is rebuilt without partitions, then as an open floor.

The floor as a block

Shopfronts and malls

Shops are part of the facade grammar, not stuck on afterwards. On a storefront face, facadeLayout groups the ground bays into shop units: it picks the trade first, weighted by the building's shop mix (everyday, high street, nightlife, mall), then the unit's width in bays from that trade's range, and seeds the dice by the face's corner in plan, so the facade, its far tier, the shop's rooms, its sign and the citysim's place all agree on what the shop is. (With the height in the hash, a pharmacy's sign once stood over a bookshop's shelves.)

Colour and lit windows

Building meshes are grouped by PartId (wall, glass, lit glass, brick, concrete, stucco, roof, trim, door, interior finishes, furniture finishes ...), one mesh per part with one material each, merged across a render cell. Colour rides on the vertices: the glass materials are white, so a pane's vertex colour is its glass (the reflectance the sky is mirrored in), and each tower gets its own tint (blue, green, bronze, smoke, silver ... by glassStyle).

At night about a third of the windows light up. Which ones is a hash of the opening's quantised world position (litWindow: (positionHash(worldPos) & 0xffu) < 85), so every LOD tier and every rebuild lights the same windows; a curtain wall lights per bay against a per-storey occupancy instead of row by row. The lit pane's colour has to carry two things, its glass by day and its lamp's tint by night, in one vertex colour:

litPaneColour: the glass in the top 7 bits of each channel, the tint index in the low bits src/engine/procgen/city/shape_grammar.cpp
Vec3 litPaneColour(const Vec3& glassCol, const Vec3& worldPos, bool curtainWall) {
    const int idx = litTintIndex(worldPos, curtainWall);
    auto chan = [](Real c, int bit) {
        int b = static_cast<int>(std::lround(std::clamp(c, Real(0), Real(1)) * 255.0)) & ~1;
        return static_cast<Real>(b | bit) / 255.0;
    };
    return Vec3(chan(glassCol.x, idx & 1), chan(glassCol.y, (idx >> 1) & 1), chan(glassCol.z, (idx >> 2) & 1));
}

The shaders (Vulkan mesh.frag, Metal and WebGPU mirrors) decode the index back into one of seven tints (office white and fluorescent blue-white behind curtain walls; incandescent, cream and the odd cool or green-white room elsewhere) and apply it to the emission only (FLAG_EMISSIVE_VERTEX_TINT). Lit panes are interior-mapped: the fragment's view ray is intersected with a room box behind the glass and samples a baked atlas of sixteen furnished rooms. Tall roofs add crown bands, signage boxes, podium uplights and flashing red aviation beacons on the FAA's height rule (ADR-0086 point 10).

The mesh audit

Every triangle the grammar emits goes through the shared mesh library (MeshBuilder, ADR-0173), which winds it to the outward normal it is given and drops it when it has no area: nobody writes index order by hand. The audit (ADR-0172) then judges every producer by one rule set: the engine's front face is clockwise seen from the normal's side, a triangle more than 107° away from its normals is inward, past 154° flipped, and a degenerate triangle is one under kNoArea2.
