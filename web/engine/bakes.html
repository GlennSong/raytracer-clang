The build cache: bakes, bundles and streaming

A city level takes minutes to generate, and the result is the same every time for the same inputs. So the engine computes it once, saves it as a bundle named by a hash of everything that went into it, and reads it back on every later load. This page explains that cache, the smaller caches beside it, how the GPU is fed from it a cell at a time, and the measured steps that took the island from a 10.5-minute first frame to under a minute.

The problem

Every level is generated from a small JSON file: a road graph, a terrain recipe, a few knobs for the city simulation. Turning that into a playable world means meshing every road deck and junction, parcelling every block into lots, growing every building from a grammar, grading the ground under it all, and handing the city simulation tens of thousands of people with homes and jobs. Before ADR-0084 a lanelab level rebuilt its city on every start: about 36 s of road building plus 30–40 s of lots and buildings, all recomputing a result that was already known. On the island (island_8_nature) the cold build is 793 s for the city and 124 s for the lots (ADR-0143) — the "28 minutes" Glenn asked about.

Three things make caching this harder than it sounds:

  • Knowing when the cache is stale. The output depends on input files and on the code. A hash can see the files; it cannot see the code.
  • Size. The island's bundle reached 8.59 GB, and every code change wrote another one. On 2026-10-04 the bake folders on this machine held 517 GB.
  • Memory. Reading the whole city into the 10 GB GPU does not fit. The cache had to become the format the world streams from, a cell at a time.

The pipeline: from level file to a loaded city

The loader calls one function, obtainForLevel. It works out every producer's key, combines them into the bundle's directory name, and either opens what is there or bakes it now. The command-line tool rt_bake and the editor's "Bake level cache" button call the same bakeLevel(), so a bake made by any of the three is the same file.

The path through obtainForLevel (src/engine/bundle/bake.cpp). RT_NOCACHE=1 skips every disk read and write and bakes in memory; RT_BUNDLE_REQUIRE=1 turns a miss into an error.

Two details make this robust. First, a bake is written into <key>.tmp-<pid> and the manifest is the last file written, so a crashed or half-finished bake never looks like a finished one; the rename into place is the commit. Second, the cold path packs and unpacks too: when the loader builds a city without a cache (say under RT_NOCACHE), it still goes through the bundle in memory, so a warm load and a cold load are the same geometry to the byte.

Inside a bundle

A bundle is deliberately dumb: a header, then sections appended one after another as producers write them, then the table of contents as JSON at the very end. Nothing in the container knows what a road or a building is. Why not glTF? ADR-0084 weighed it: tinygltf parses and copies the whole buffer, is float-only, caps a file at 4 GB and cannot memory-map or read part of a file — and partial reads are exactly what a streaming loader needs.

One bundle on disk. The header is patched last with where the table of contents landed; the reader maps the file once and hands out views into it.

The 64-byte header, written first and patched with the TOC's position at the end src/engine/bundle/bundle.cpp
constexpr char kMagic[4] = {'R', 'T', 'B', 'N'};
constexpr uint32_t kEndianMarker = 0x01020304u;

// Header (64 bytes, little-endian): magic[4] u32 major u32 minor u32 endian u32 realBytes u32 reserved
// u64 tocOffset u64 tocSize u64 sectionCount u64 reserved u64 reserved.
std::vector<uint8_t> headerBytes(uint64_t tocOffset, uint64_t tocSize, uint64_t sectionCount) {
    BinWriter w;
    w.append(kMagic, 4); w.put<uint32_t>(kFormatMajor); w.put<uint32_t>(kFormatMinor); w.put<uint32_t>(kEndianMarker);
    w.put<uint32_t>(static_cast<uint32_t>(sizeof(Real))); w.put<uint32_t>(0);
    w.put<uint64_t>(tocOffset); w.put<uint64_t>(tocSize); w.put<uint64_t>(sectionCount); w.put<uint64_t>(0); w.put<uint64_t>(0);
    w.bytes.resize(kHeaderBytes, 0);
    return w.bytes;
}

Each section's contents is the job of a codec in bundle/codecs.cpp, and every codec writes its own magic and version first (MESH, CMSH, RTHT for height tiles…). A reader that meets a version it does not know returns false, which the loader treats as a miss for that one producer. So compatibility has four layers, all in the manifest: the container format (hard), each codec's version, each producer's key, and the engine's own identity (a git describe string, compiler and build type), which is recorded but only enforced with RT_BUNDLE_REQUIRE_ENGINE=1.

Producers and keys

A producer is a small interface. The bake runs every producer that applies() to the level, in name order, and each one writes sections under its own name.

BundleProducer: what a stage of the bake has to say about itself src/engine/bundle/bake.h
class BundleProducer {
public:
    virtual ~BundleProducer() = default;
    virtual std::string name() const = 0;
    virtual bool applies(const LevelInputs& in) const = 0;
    virtual ProducerIdentity identity(const LevelInputs& in) const = 0;
    // Writes every section under "<name()>/...". The progress fraction it reports is LOCAL (0..1 of this producer).
    virtual ProducerReport produce(const LevelInputs& in, BundleWriter& out, const ProgressFn* progress) const = 0;
    virtual double weight() const { return 1.0; }   // relative cost, for the overall progress fraction
};

The interesting method is identity(). It must hash every input the producer reads, because anything it leaves out can change without the bake noticing. Here is the lots producer's: its tag and record format, then the city producer's own key (so new roads always mean new lots), then the level blocks and Lua files it reads. Note what it deliberately leaves out: the forest, which the lots never read, so a tree-species tweak on the island does not re-bake its city.

The bundle's folder is named by all the producers' keys together, sorted by name so the order of registration does not matter:

combinedKey: one directory name for the whole level src/engine/bundle/bake.cpp
uint64_t combinedKey(const std::vector<std::pair<std::string, uint64_t>>& producerKeys) {
    std::vector<std::pair<std::string, uint64_t>> ks = producerKeys; std::sort(ks.begin(), ks.end());
    uint64_t h = fnv1aStr("rt-level-bundle"); h = fnv1a(&kFormatMajor, sizeof(kFormatMajor), h);
    for (const auto& k : ks) { h = fnv1aStr(k.first, h); h = fnv1a(&k.second, sizeof(k.second), h); }
    return h;
}

The keys chain. No stage has to remember to invalidate the next one: the next one hashes what came out of it.

When to bump a tag

The key cannot see code. When a change alters what a producer outputs for the same inputs, someone has to change its tag by hand, or the old bundle keeps loading and looks current. That is the one failure the cache cannot catch by itself (docs/bakes.md lists it, with "an input the lots stage reads that is not in its key", as the two uncaught cases). The rules, from docs/bakes.md:

ChangeBump
Anything the lot pass outputs: sculpting, massing, lot selection, grading, a part meshkLotsBuildTag (lots_producer.cpp; now "2026-10-23.3")
The roads the lanes builder makeskLanesBuildTag (city_producer.cpp; now "2026-10-23.1")
Track and stationskRailBuildTag (folded into the city key only for graphs with track)
The lot record's fieldskLotsFormatVersion + a field in tests/test_lot_cache.cpp
Interiors, furniture, the citysim, rendering — anything built at load, not read from the bundlenone

A bump replaces the tag's comment with the reason for this bump; the history lives in the commits (git log -G kLotsBuildTag). Because a bump makes every level's bundle stale and the level suite then re-bakes everything it loads, the advice is to iterate with RT_NOCACHE=1 and bump once the change has settled.

Copying forward and sharing blocks

Changing one producer's inputs should not rebuild the others. When bakeLevel finds an existing bundle whose manifest carries a producer's current key (a "donor"), it copies that producer's sections across instead of running it. Producers can also read each other's output through the bundle under construction — BundleWriter::readBack — which is how lots gets the city's ground and block holes without a side channel, whether the city was rebuilt this run or copied.

That still wrote a whole new multi-gigabyte file each time. The 2026-10-05 addendum to ADR-0084 measured why it hurt: a day of lots-tag bumps wrote about 270 GB of near-identical bundles. It also measured that a bake is deterministic (a from-scratch rebake of metro_v2_test matched the cached bundle in 1643 of 1643 sections) and that a typical change touches a few cells. So file bundles now align every section to 4 KB, and a new bundle clones any section that comes out identical to one in the level's previous bundle, using the Linux FICLONERANGE ioctl. On btrfs the two files then share those disk blocks.

On a filesystem that cannot share blocks (tmpfs, ext4, macOS) the bytes are simply written. Measured: a rebake of metro_v2_test after a one-line campus change wrote 3.4 MB of 1.07 GB. The caches beside the bundle

Some things cannot be baked from the level file alone, because they need what the loader has built first. These are cached the same way — named by a content hash of their inputs — but filled on the first load after a change rather than by rt_bake.

The terrain pyramid (ADR-0095)

Before the pyramid, the ground's height was a formula evaluated per vertex at run time, and the CDLOD terrain's finest cell was tied to a fixed level count, so when the world grew it coarsened to 11.7 m and buried streets beside graded lots. The pyramid samples the final ground once — natural terrain, carved roads, terraces, every lot pad — into a quadtree of 129 × 129 tiles of uint16 heights. It is sparse: a tile's four children are kept only where the parent, drawn as triangles, misses them by more than 2 cm. Plains stop early; streets and pad edges go down to 1 m cells.

HeightTile: 33 KB of heights instead of ~1 MB of vertices src/engine/procgen/height_pyramid.h
struct HeightTile {
    TileKey key;
    float minH = 0.0f, maxH = 0.0f;
    float step = 0.0f;         // quantization step (m)
    float error = 0.0f;        // vs the level below, as drawn (0 at level 0)
    bool hasChildren = false;
    std::vector<uint16_t> q;   // kTileSamples^2, row-major (z rows, x columns)

    double at(int i, int j) const {
        return static_cast<double>(minH) + static_cast<double>(q[static_cast<std::size_t>(j) * kTileSamples + i]) * step;
    }
    // Height at local cell coordinates (0..kTileCells), interpolated across the triangle
    // split the mesher emits: (a,b,d) when u >= v, else (a,d,c) -- a the cell's min corner,
    // d the max (terrain_lod.cpp, lodSurfaceHeight).
    double sampleLocal(double gx, double gz) const;
};

The pyramid is written in the same bundle format (one terrain/L<level>/<tx>_<tz> section per tile) and cached under cache/terrain/, keyed by the ground's content plus the pyramid's spec. On metro_planned it is 4,501 tiles, 142 MB, built in 7.9 s on all cores when it misses (commit 463a6d8e). Since ADR-0225 it is also the fast answer to "how high is the drawn ground here?": a baked level reads it in about nine hash lookups instead of evaluating the field (about 50 µs a sample over the city), which is what made grass streaming affordable.

The population cache (ADR-0143)

Assigning every agent a home, a job, an errand stop, doors, hours and a commute took 5.5 s on the island. It is deterministic, so it is cached too. The key hashes everything assignPlaces reads; a hit restores each agent from a fixed-size record.

It is a cache, not a bake stage: a producer only sees the level's input files, but the population needs the nav graph, the places and the fleet, which exist only once the level has loaded. RT_POPULATION_VERIFY=1 decides anyway and compares; on the island it reported 0 of 28,000 records different. assignPlaces went from 5.5 s to 0.14 s.

How the load times fell

The work came in a few concentrated pushes, each driven by a measurement. The timeline below is the centrepiece: above the line, time to load; below it, bytes on disk and on the GPU.

The island: 634 s to 53 s (ADR-0143)

Glenn's question was "is it going to take me 28 min to load that city?". The measurement split it in two: the 28 minutes was a cold cache (city build 793 s plus lots 124 s), paid once. But even with the bundle warm, the level loaded in 103 s and the first frame came at 634 s. Profiling was by stack sampling (no perf on this box: eu-stack in a loop against the viewer's PID, counting engine:: frames), then the largest cost first, each change checked to give identical answers:

  1. "There and back?" is a component test. The city sim ran two A* searches per candidate home/work pair (up to 24 candidates for each of 28,000 agents); every failed search on an island of separate street networks flooded everything reachable. One strongly-connected-components pass (engine::stronglyConnected, iterative Tarjan) answers every pair. 33,012 random pairs agreed with the route search. Playable 634 → 117 s.
  2. Pads clipped against the blocks they touch. All 12,856 lot pads were clipped against the union of every block, built quadratically: about half of the level load. Now each pad is cut against the block pieces its bounds touch. Level 103 → 40 s; playable → 61 s.
  3. The population cache (above). Playable → 53 s.

What was left, and a later number. ADR-0143 lists the rest of the ~53 s, each part deterministic and cacheable the same way: forest rock placement (~7 s), blocks from road holes (~7 s), physics mesh shapes (~6 s), the rest of the city sim start (~7 s), drawn roads (~4 s). A month later ADR-0225 measured an island load of 187 s, cut to 169 s by reading the ground from the pyramid. That figure came from the fly-probe harness on a later state of the level, and the ADRs do not reconcile it with the 53 s; treat them as separate measurements.

Smaller on disk: the stored vertex is the uploaded one

By October the island's bundle was 8.59 GB, 6.64 GB of it building parts, each stored as raw float32 planes. ADR-0224 stores a mesh the way the GPU will take it anyway: the 32-byte standard vertex of ADR-0096, but with an exact float normal, then compressed losslessly with meshoptimizer's vertex and index codecs.

CompactVertex: 40 bytes, then meshoptimizer over the stream src/engine/bundle/codecs.cpp
// The Vulkan GpuVertexPacked, but for the normal: that stays exact, because the loader re-derives world-planar UVs
// from it (applyWorldPlanarUVs) and at island coordinates an oct normal's 5e-5 rad would move u by ~0.25 m
struct CompactVertex {
    float position[3];
    float normal[3];
    int16_t tangent[2];
    float texcoord[2];
    uint8_t color[4];
};
static_assert(sizeof(CompactVertex) == 40, "the standard vertex with an exact normal");

void putEncoded(BinWriter& w, const void* data, size_t count, size_t stride) {
    std::vector<uint8_t> buf(meshopt_encodeVertexBufferBound(count, stride));
    buf.resize(meshopt_encodeVertexBufferLevel(buf.data(), buf.size(), data, count, stride, 3, 1));
    w.putVec(buf);
}

Why keep the normal as floats? The loader re-derives world-planar texture coordinates from it; on a round tower far from the origin an octahedral normal's tiny error would make the brick joints zigzag. Positions and UVs stay exact so neighbouring cells still meet bit for bit; a tint outside [0, 1] or a tangent that carries data keeps a float plane. What is lost is only what the upload drops anyway: the tangent's length and tint precision past 8 bits.

Streaming ahead of the camera

A bundle cell is a render cell, which is what lets the world stream. engine::Residency (ADR-0095) holds one item per cell and tier: where it is, the distances at which it is wanted, and a two-phase load — prepare() on a worker thread (read from the bundle, decode, drape), then commit() on the render thread (upload, create entities). Each building cell has three tiers: full detail near, flat facades further out, and a mass-box stand-in that is always resident.

The rings are schematic, not to scale. Figures are from residency.h/.cpp and ADR-0149/0226.

Residency::update: measure distance from where the camera will be src/engine/residency.cpp
    // AHEAD OF A MOVING CAMERA (the city's next ten #10, a fly-around): where it will be in ~0.75 s at this frame's
    // step (45 frames), so a cell starts streaming before the camera is on it; an item counts as near when it is near
    // either point. And when moving fast (over ~90 m/s at 60 fps) twice the prepare jobs.
    Vec3 ahead = camera;
    double step = 0.0;
    if (haveLast_ && !jump) {
        const Vec3 d = camera - last_;
        step = std::sqrt(d.x * d.x + d.y * d.y + d.z * d.z);
        ahead = camera + d * 45.0;
    }
    const int maxPreparing = step > 1.5 ? 2 * kMaxPreparing : kMaxPreparing;

How it got here. The first residency client (b4d985ea) promised "a brief loss of detail, never a hole", but the stand-in proxies only drew beyond the facade distance, so inside that ring a cell whose tiers had not arrived drew nothing. Every aerial shot after a camera jump showed bare blocks. ADR-0149 made the stand-ins cover (a count per cell; while it is zero the proxies draw at every distance), added the look-ahead, and made jumps stream. A scripted fly across Saltwood at 200 m/s went from empty blocks beyond the first streets to full detail throughout. Two weeks later grass got the same treatment (ADR-0225: 3D distance, half the job pool, the same 0.75 s horizon; bare tiles 921 → 0), and tiers stopped popping (ADR-0226: a 0.35 s dither crossfade, p99 frame time unchanged at 24.6 vs 24.8 ms).

A cache keyed by what it describes (ADR-0241)

Streaming exposes a classic caching bug, and the indoor cache is the worked example. A tower streams its interior in storey windows: the street window has shop units, a window at storeys 32–37 has none. The city renderer cached each building's shop-unit-to-place list by building id the first time its interior was seen. Swinging on the grapple from the street to the 40th storey in seconds, the cached list had N units while the new interior's table had room for one, and stepIndoors wrote one byte past it. The viewer crashed with free(): invalid next size far away in unrelated code; an AddressSanitizer build named the real write.

The fix: the entry records which interior it was made for src/apps/citysim/city_render.h
    // `unit` is by the index of the interior's shop units, so it holds only for the interior it was made for: a tower
    // streams its interior in storey windows, and the ground floor's (shops) and the 40th's (none) differ -- `units`
    // says which one this is (their count and floor heights), and a different one is matched afresh (#114: a cached
    // list of N units indexed a 1-entry table when the player swung from the street to the top floors)
    struct BuildingPeople { PlaceId whole = kNoPlace; std::vector<PlaceId> unit; std::vector<double> units; };
    std::unordered_map<int, BuildingPeople> buildingPlace_;

It is the same rule the bundles follow, at a smaller scale: a cache's key must name everything its contents depend on. "This building" was not enough; "this building's interior, with shop units at these heights" is. The check was 320 visits into the 12 tallest downtown towers under ASan, 225 window changes rematched, no report (tools/asan_storey_probe.py).

Housekeeping: pruning old bakes

Nothing deletes an old bundle automatically. Every tag bump, engine change and level-suite run writes a fresh one, and by 2026-10-04 the buildings worktree held 517 GB of level bundles and 39 GB of pyramids: 304 bundles, of which 22 were the newest for their level. Shared blocks made each new bundle cheap, but the old ones still pin blocks the newest no longer uses.

rt_bake --audit <dir>every baked mesh through the mesh audit (ADR-0172)
rt_bake --prune [--yes] [level.json …]list (or delete) every bundle not the newest for its level and not the current bake of a listed level, then the terrain and population files every level that used them has moved on from
rt_bake --glb / --glb-split cellalso export the city as glTF for Blender: an export view, not the cache

Terrain and population files are named by a content hash, so levels that build the same ground share one. Since ADR-0256 each has a record beside it (<file>.uses): the levels whose loads used it, and when. The prune deletes one once every level that used it has used a newer file of its kind, and keeps a shared file while any of its levels still uses it. Files from before the records are kept; Glenn's rt-bake-cleanup skill (~/.claude/skills/rt-bake-cleanup/prune_bakes.py, outside the repo, dry run by default) ages those out by date across every checkout.

The trap. "Newest" is not "current". Running old code (a baseline checkout, then the level tests) bakes newer bundles under old keys; a prune after that keeps those and deletes the current ones. On 2026-10-14 island_8, metro_lanes and river_town had to be rebaked for this reason. Prune before an old-code run, or check rt_bake --status on each level first and pass the levels to keep.

When a change does not show, docs/bakes.md has a recovery ladder, least drastic first: run once with RT_NOCACHE=1 (if that fixes it, the bundle is stale); rt_bake <level> --force and then find the missing tag bump or key input; drop that level's folders; and last, rm -rf cache/levels cache/terrain cache/population — always safe, since every one of these is a cache.

Still owed (memory note rt-bake-cache-housekeeping, docs/bakes.md): RT_BUNDLE_VERIFY (rebuild in memory and compare section hashes, nightly, to catch a forgotten tag bump); the level suite pruning after itself.
